# Changelog

## v1.2.0 - 2026-10-03

- Made every template change a released version with its own English changelog entry. `CHANGELOG.md` no longer has an `Unreleased` section: each change adds a dated `## vX.Y.Z - YYYY-MM-DD` section, and `make template-release-prepare` refuses to prepare a release whose newest changelog section is not the version being prepared. `make validate-template-docs` now rejects `Unreleased` headings, malformed release headings, non-descending releases, an empty newest release section, and a newest version that is neither the current `project/state.yaml` `template.version` nor exactly one `patch`/`minor`/`major` bump ahead - the permissive window that lets a release be prepared before the version commit exists. A separate strict state/content gate, `make validate-template-release-ready`, requires the newest changelog release to equal `template.version`. Template CI then runs `make validate-template-release-boundary`, which proves the PR tip itself introduces that version relative to `HEAD^1`; the version-transition commit must be final so merge, squash, fast-forward, and rebase histories remain taggable. Agent instructions and the template development, architecture, and release documentation require choosing a SemVer bump and writing the versioned changelog entry as part of the same change.
- Added a role-based, cost-aware agent execution policy (issue #24): `.agents/execution.yaml` is the single visible source of truth for how each engineering operation runs and keeps five concepts separate - **skill** (the operation), **role** (`planner`, `implementer`, `reviewer`, `fixer`), **profile** (reusable cost/capability policy such as `reasoning-high`, `coding-efficient`, `utility-cheap`), **harness** (`codex` today, `local` later), and **model** (an opaque configured detail where `null` inherits the harness default). `make agent-route ROLE=<role> [FORMAT=json]` resolves `role -> configured policy -> profile -> decision` deterministically and reports status, role, profile, harness, model, reasoning effort, capabilities, escalation, and budget; the resolver is the pure `template/tools/agent_execution.py`, emitted for every profile while `make agent-route` is exposed only in managed projects. Policy is fail-closed: unknown keys and trigger-inapplicable escalation fields are rejected before resolution; `policy` carries deterministic retry/review limits (`max_implementation_attempts`, `max_review_cycles`) that return a blocking/human decision instead of another attempt; and `escalation` holds the only ways a role may change profile (`implementation_failure`, `architecture_failure`, `external_blocker`), so an agent can never silently promote itself to a stronger, costlier profile. Budgets are configuration only (`task`, `session`, `campaign` scopes) and compare a configured ceiling against harness-reported usage; a ceiling with unknown cost or a missing usage scope blocks and asks a human instead of pretending the budget is safe, and the public `evaluate_budget` seam validates execution policy and structured usage, including budget scope and harness-reported cost, so budget enforcement remains a safe standalone contract. This adds structured review and invocation contracts, deterministic escalation and budgets, and opaque harness/model configuration; it deliberately adds no orchestration, so generated projects keep their simpler `edit -> check -> done` flow.
- Separated implementation validation from CI and proved the multi-session workflow (issue #29): template authoring now names three validation boundaries - focused, change-aware implementation checks (`recommended_checks` stays canonical), exactly one canonical local pre-review gate per review cycle (`make agent-pre-review TASK=<id>`, which runs `make check` exactly once and never `release-check`), and exhaustive asynchronous CI. Routine implementation no longer duplicates `make check` immediately before pre-review, and the implementation session ends at task-in-review/pushed instead of waiting for or polling GitHub Actions. A new deterministic golden path (`tests/test_agent_multi_session_workflow_golden_path.py`) proves the multi-session loop end to end - implementation, bounded handoff, focused `MODE=resume` over a 30+ change branch, the PR boundary, a simulated exhaustive-only CI failure after local pre-review passes, and a fresh CI-repair session that preserves the same task/branch/worktree/claim/pull request, repairs with focused checks, and runs one pre-review per repair cycle. Generated projects keep their simpler fast-checks -> final-local-check -> CI flow; actual template release preparation still uses `make release-check`.

- Added an optional, ephemeral `FOCUS` working-set selector for resume context (issue #28): `make agent-context TASK=<id> MODE=resume FOCUS="<path> ..."` now eagerly loads only the explicit repository-relative files a fresh session needs while the complete branch change set stays authoritative and observable - so `branch scope != session working set`. `resolve_context(task_id, skill, mode, focus)` gained a structured `focus` input; focus applies to `MODE=resume` only (a focus in another mode is rejected), accepts exact paths only, is never persisted, and never changes task identity, branch, worktree, claim, lifecycle, dependencies, approval, the complete changed-file metadata, diff safety, ownership validation, or the `recommended_checks` derived from the whole branch. Every focus path is validated against the existing exclusion/sensitive policies and must stay inside the repository, so traversal, absolute paths, escaping symlinks, missing files, directories, and sensitive/excluded files are rejected. Focused files (changed or not) are protected eager candidates; non-focused changed files remain visible as metadata with an `outside focus` omission reason and stay discoverable through the existing search roots; and `FORMAT=json` gains deterministic metrics (`branch_changed_files_count`, `focused_requested_files_count`, `focused_loaded_files_count`, `eager_files_count`, `total_bytes`) plus `focused_files`/`focused_loaded_files`/`focus_enabled`. `MODE=new` and `MODE=resume` without `FOCUS` are unchanged, so ordinary single-session and small generated-project tasks are unaffected; the T-032 handoff stays the durable-work surface and carries no focus state.
- Separated managed tasks from agent sessions (issue #27): one managed task may now span several sequential fresh agent sessions because `make agent-handoff TASK=<id>` (and `FORMAT=json`) renders the durable state a new process needs - task/lifecycle/approval identity, dependencies, branch/HEAD/worktree/claim ownership and dirty state, a compact branch-aware changed-file summary that keeps the branch/staged/worktree/untracked source and deletion state (with accurate total/deleted and omitted counts but no second unbounded deleted-path list), a bounded set of recent task commits, the remaining acceptance criteria, the lifecycle next action, the checks resolved by the same context routing, deterministic resume commands, and small metrics (`changed_files_count`, `recommended_checks_count`, and `handoff_bytes`, the exact UTF-8 size of emitted `FORMAT=json`). The handoff is derived, runtime-only, deterministic, bounded at 8 kB, and never persisted, so it carries no session id, session record, transcript, reasoning, diff, log, or command history, and requesting it from the wrong task or worktree fails loudly. The new `template/tools/agent_handoff.py` owns the structured `AgentHandoff` model plus its JSON and concise human rendering, while derivation reuses the canonical task, effective-status, ownership, branch-aware diff, and check-routing seams in `template/tools/agent.py`; the module and the managed-only `agent-handoff` Make target are excluded from lightweight generation. Ordinary implementation context also stopped eagerly loading routing-only and planning context: `implement-change` no longer reads `.agents/context-map.yaml` or the `Makefile` because `make agent-context` resolves them, and `managed.files` now carries only `project/state.yaml` while the task-selection, planning, and reassessment skills read the dashboards they actually need.

- Enabled safe parallel multi-agent development in generated managed projects (issue #18): `make agent-worktree TASK=<id>` now claims a task atomically, creates a deterministic `task/T-###-<slug>` branch, and adds a worktree outside the tracked tree (sibling `<project>-worktrees/`, or `PROJECT_WORKTREE_ROOT`), so one task maps to exactly one claim, branch, worktree, agent, and pull request. New modules `project_tool/worktrees.py` (Git worktree/branch mechanics) and `project_tool/claims.py` (local claims and worktree ownership resolution) keep Git mutation out of read-only `git.py` provenance, and `make agent-status` now derives the owned task from the current branch and claim instead of being told. Claims are local, uncommitted, atomic (`O_CREAT|O_EXCL`), deliberately not freed by process death, inspectable with `make agent-worktrees`, and explicitly releasable with `make agent-claim-release`; `make agent-worktree-remove` refuses dirty worktrees and unique unmerged commits unless `FORCE=1` is passed. Several independent tasks may now be `in-progress` at once, `project/state.yaml` no longer carries `work.active_task`/`work.blocked` (a legacy `work` section is ignored), lifecycle transitions rewrite only the task record, and committed dashboards keep project-global rows only - so parallel task branches no longer conflict in shared Markdown while dependency, A1/A2 approval, PR-association, and human-merge completion semantics stay canonical.
- Reworked the template release workflow into a PR-only, two-phase flow: `make template-release-prepare BUMP=<major|minor|patch>` creates an ordinary, reviewable `chore(release): vX.Y.Z` version commit on a non-`main` release branch (no tag, no push), and `make template-release-tag` creates the annotated release tag only after that commit is merged to `main` and local `main` equals `origin/main`. Publication pushes only the intended tag (`git push origin vX.Y.Z`). Direct release commits on `main`, `git update-ref` branch advancement by release tooling, and the `git push origin main --follow-tags` publication recommendation are removed.
- Added a supported Copier update workflow for projects generated from a versioned Git template source.
- Documented the template-owned, project-owned, and merge-sensitive file ownership model.
- Added a targeted two-version Copier update integration test using temporary Git commits and tags.
- Recorded template version metadata in generated projects through `.template-version` rendered from the Copier Git ref.
- Current limitation: update safety is tested for the fullstack-local golden path; future structural migrations require explicit migration tests.
- Refined generated project-state reconciliation so managed projects keep stronger reconciliation (including a `Project State Check`) while lightweight projects only keep durable planning/status artifacts truthful when present.
- Agent efficiency v1: three-tier context loading, skill-aware `make agent-context TASK=<id> SKILL=<skill>`, `files` vs `search_roots` context-map semantics (schema v2), deterministic `budget` with omission reporting, branch-aware changed-file detection, change-aware recommended checks, one canonical full `make check` gate in `agent-pre-review`, a resume/review-fix `MODE=resume`, and concise durable task-record guidance.
- Simplified the managed approval lifecycle for GitHub-backed projects: in `workflow_mode: pr` the human GitHub merge of a task's pull request is the A1 approval/completion boundary (and A2's completion boundary). Agents move A1/A2 work to `review`, associate one task id (`T-###`) per pull request, and stop; `make pr-validate` checks pre-merge structural readiness; A1 `task-approve` and A1/A2 `task-complete` are rejected in `pr` mode; boards/dashboards derive the completed view; and no post-merge lifecycle command or cleanup pull request is required. `local`/`branch` mode keeps the explicit human `task-approve` + `task-complete` fallback, and historical `done` approval metadata remains valid.
- Made PR-mode derived project state post-merge consistent. Merge-derived status (effective completion, waiting state, dependency completion, recommended next action, and merge annotations) is now rendered at read time by `make project-status`, including the live merge-aware board. Committed generated blocks in `README.md`, `project/index.md`, and `project/board.md` keep only content that already follows from the canonical task records, so a human merge no longer produces false drift or requires a lifecycle-only synchronization commit. Drift validation stays exact for that deterministic content and rejects re-introduced Git-relative rows in `pr` mode; `local`/`branch` persistence is unchanged.
- Reduced template-authoring change amplification (issue #17): the root `.agents/`/`.codex/` agent layer is now the canonical source for the `template/` mirrors (`tools/agent_layer.py` with `make sync-agent-layer` and drift-checking `make validate-agent-layer` wired into `make check`/`make release-check`); the root `.agents/context-map.yaml` routes each template surface to a narrow neighborhood with focused check recommendations (`test-agent`, `test-lifecycle`, `test-static`, `test-backend`, `test-frontend`, `test-python-profiles`, `test-mirror`, exact test-file runs) while keeping the deterministic `make check` fallback and full release validation; and focused mirror/routing tests plus a ranked authoring-cost audit document the evidence. In `workflow_mode: pr` the routing stays repository-authoring only: the mirrored `template/` agent-layer trees are editorially identical to their canonical root files, and the `template/` dashboards remain deterministic persisted views, so nothing here changes merge-derived status ownership.
- Refactored the generated project-governance tool (issue #19) from the 1837-line `template/tools/project.py` monolith into a small package behind an unchanged CLI: `template/tools/project.py` is now a thin parser/dispatch/error-handling layer (147 lines) with the compatibility exports that `tools/agent.py` and the maintainer release tool load by path, while `template/tools/project_tool/` owns the model, storage/parsing, Git merge provenance, lifecycle policy, persisted-versus-runtime rendering, project/task validation, documentation validation, the explicit mutation boundary, and the command implementations. Imports stay one-directional with no cycles or generic utility module, `python tools/project.py ...` and every Make target are unchanged, the lifecycle and T-029 persisted/runtime ownership semantics are untouched, new modules avoid the old file-wide type suppressions, the package is excluded from lightweight generation, and Copier updates now propagate changed package modules. `.agents/context-map.yaml` routes `template/tools/project_tool/**` to a fast module-seam test neighborhood plus the canonical lifecycle checks.
